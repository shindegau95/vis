Design system choice — explained, no jargon

2026-05-23 · Author: Gauravprakashshinde · Rendered after jargon callout
The choice in front of you: what set of building blocks sits under Vis's custom-built orb / Equipment-Aware Logger / PR Moment components, doing the boring-but-critical work (dialogs, focus management, accessibility, theme switching). Three paths. Every term defined below before you decide.

Glossary — the terms you'll see in this doc

If you already know it, skim. If you don't, every term is one sentence.

React Native (RN)
Meta's framework for writing iOS + Android apps in JavaScript / React. You write React code; it renders as real native iOS and Android UI (not webview). You already know React — RN is the same mental model.
Expo
A toolkit on top of React Native that makes setup easier and adds OTA updates + simpler access to phone hardware (camera, push notifications, etc).
OTA (Over-the-Air) update
Pushing a JavaScript fix to users' phones without going through Apple's / Google's app-store review (which takes a day or more). You ship a bug fix → users get it on next app open. Only works for JS/CSS changes; native code still needs store review.
WCAG 2.1 AA
The international standard for making apps usable by people with disabilities — text contrast ≥ 4.5:1, screen-reader labels on everything tappable, keyboard navigation, no flashing animations. "AA" is the level Vis targets (industry baseline). Required for India DPDPA + EU GDPR + good practice.
a11y
Short for "accessibility" — the 11 letters between "a" and "y." Same idea as WCAG-compliance, just shorter.
Tamagui
A UI toolkit for React Native (and the web). The key feature for Vis: its theme tokens (color + font definitions) look exactly like the two-layer token system we locked in step-05. Swapping themes (light/dark, or future user accent presets) is one config change instead of dozens of component rewrites.
Tailwind CSS
A way to style web pages by writing short class names (bg-amber-500, p-4) instead of writing CSS files. Used on the Angular admin web. Lets the admin styling stay in sync with the same Vis tokens.
Angular CDK (Component Dev Kit)
An Angular library of unstyled, accessibility-correct building blocks: dialogs, focus traps, overlays, drag-and-drop. Headless means it does the hard a11y work but doesn't impose any visual design. You style it yourself to match Vis.
Reanimated 3
React Native's animation library. Runs animations on the phone's native graphics thread instead of JavaScript — animations don't stutter while the app does other work (loading data, etc). Needed for smooth Equipment-Aware Logger gestures (drag the pin, snap a plate).
Lucide
An open-source icon set with line-style restrained icons. Has both a React Native version and an Angular version, so all three apps use the same icons.
Flutter / Dart
Google's competing framework — write phone apps in the Dart language; one codebase for iOS + Android. You don't know Dart, so switching costs time you'd save elsewhere.
Kotlin Multiplatform (KMP) + Compose
JetBrains' competing approach — write business logic in Kotlin once, ship to iOS + Android + Wear OS. Strong on Wear OS. You don't know Kotlin.
SwiftUI
Apple's official framework. Required by Apple for Apple Watch apps starting watchOS 10+. No way around it for Watch.
Wear OS
Google's smartwatch operating system. Watches from Samsung, Google Pixel Watch, OnePlus, etc. Apps written in Kotlin + Compose.

The Apple Watch / Wear OS reality (read this first)

No framework gives you "one codebase for phone + watch." Anyone who claims otherwise is selling something.

  • Apple Watch = SwiftUI required by Apple. React Native, Flutter, Kotlin Multiplatform — none of them work on Watch in production. This is Apple's rule, not a framework limitation.
  • Wear OS = Kotlin + Compose is the official path. Flutter has limited beta support. RN doesn't work on Wear OS.
  • What you actually share across platforms: the backend API and the data models. Phone app, Watch app, and Wear OS app all talk to the same Spring Boot backend with the same data shape. The UI is built per platform; the logic is shared.
  • How Strava, Trainerize, Bevel do it: Phone in React Native or native Swift/Kotlin. Watch in SwiftUI (separate codebase). Wear OS in Compose (separate codebase). All three consume the same REST or GraphQL API.

Implication for Vis: if you eventually want Watch + Wear OS (PRD §6.2 lists this as v2), you will ship additional codebases for them no matter what framework you pick for the phone today. So the framework choice today is about phone + admin web — not about Watch.

The three paths — re-explained plainly

What you're picking: which library sits under Vis's custom orb / logger / PR Moment components, doing dialogs, focus, accessibility, and theme switching.

★ Recommended

Path B — Tamagui (RN) + Tailwind + Angular CDK (web)

Stay on React Native + Angular (your current skills). Add Tamagui underneath the React Native code for theming + ready-made dialogs. Add Tailwind + Angular CDK underneath the admin web. Your custom Vis components (orb, logger, PR Moment) sit on top.

Pros

  • Uses skills you already have (React, Angular)
  • Tamagui's theme system maps 1-to-1 to the Vis token system we locked in step-05
  • Theme swap (light/dark, future accent presets) is one config change
  • Angular CDK handles the boring a11y work (focus traps, screen-reader labels) for free
  • Faster to v1 than building everything yourself
  • When you add Watch in v2, this stack survives — Watch is separate code regardless

Cons

  • Tamagui has a learning curve (~1-2 weeks for fluency)
  • Tailwind + Tamagui = two slightly different styling languages (one for RN, one for web). Bridged by shared token file.
  • Need to maintain the Lucide icon library port for both React Native and Angular

Path A — Pure custom (no UI library underneath)

Stay on React Native + Angular but build every primitive yourself from scratch — every dialog, every focus trap, every overlay. Maximum control. Maximum cost.

Pros

  • Zero risk of a library "leaking through" your custom brand
  • No vendor lock-in
  • Smallest app bundle size

Cons

  • You hand-roll all a11y / WCAG work — months of effort, risk of failing the standard
  • Slowest to v1 — every dialog, modal, focus trap from scratch
  • Tests, bug fixes, edge cases all on your team forever

Path C — Off-the-shelf libraries (React Native Paper + Angular Material)

Fastest to start. But these libraries impose Google's Material Design visual style. Vis's cinematic amber aesthetic actively fights that. You'd spend time overriding every default to look like Vis, eating back the speed gain.

Pros

  • Largest off-the-shelf component coverage
  • Mature accessibility
  • Fastest initial scaffold

Cons

  • Material Design looks nothing like Vis — every component needs heavy restyling
  • Brand-dilution risk: "looks like every other Material app"
  • Overriding Material themes is harder than building custom on Path B's foundation
