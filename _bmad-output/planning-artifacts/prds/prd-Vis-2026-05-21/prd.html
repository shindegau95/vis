1. Vision

Vis makes progressive overload effortless for anyone who lifts — solo or with a trainer. Where competitors force gym-goers to type weights and remember last week, Vis logs through visual gestures that mimic the equipment in front of you: drag the cable pin, snap plates onto a bar, slide the dumbbell rack. Where competitors silo lifters, trainers, and gyms into three apps, Vis is one product where a trainer and client can edit the same set log live during an in-person session — and where a gym can run that experience across all its branches.

Free at launch. Global from day one. India-anchored, cinematic in feel, evidence-based in method.

Three load-bearing assertions

01
Visual equipment-aware logging is THE differentiator. Primary user pain is remembering + inputting progression. Beauty serves usability. Grounded in domain research §competitive-landscape: existing apps (Hevy, Strong, FitNotes) require typing every weight; AI-coached apps (FitnessAI, Caliber) abstract the lift to text prompts.
02
Real-time trainer↔client co-edit + multi-branch ops are the structural moats. Anti-positioning: Trainerize treats trainer-client as async messaging; FitBudd does multi-branch but no co-edit; Bevel does in-person device-sharing but no real-time sync. Vis is first to unify all three.
03
Free v1; pricing later. Global units (kg + lb), per-locale dates, time zones, multi-currency-ready data model day 1.

A trainer may simultaneously hold Solo Trainer plus Gym Trainer roles at multiple brands. A client may hold Gym Client at one brand plus Solo Client of an independent trainer in parallel. The PT-relationship state is orthogonal to gym membership.

2.2 Jobs To Be Done

  • Client (any path): "Tell me what to do next, and let me log it without typing." Remove cognitive load + input friction.
  • Client (PT-attached): "Let me train with my trainer, not around them." Real-time co-edit, prescribed-vs-actual loop, PR moments.
  • Trainer: "Give me one place to author programs, track every client's adherence, and coach during the session — across all my clients."
  • Gym Staff: "Let me run member ops without spreadsheets." Roster, PT activation, payment logging, reminder cadence, CSV import day one.
  • Gym Owner: "Show me which branches and which trainers are working — and which aren't." Cross-branch revenue, adherence, retention.
  • All: "Make my data feel mine, my equipment feel mine, my progress feel earned." Cinematic, equipment-aware UI; PR moments worth sharing.

2.3 Non-Users (v1)

  • Group fitness classes / class-based bookings — out of scope (v2 candidate).
  • Apple Watch / Wear OS companion users — explicitly deferred (post-v1; addendum §5).
  • Member-facing web portal — clients are mobile-only.
  • Walk-in / non-paying members — only PT-active or self-onboarded users get the Client App.

2.4 Key User Journeys

UJ-1. Priya and Aarav co-edit a lat-pulldown session, live.

Personas: Priya (Gym Trainer), Aarav (Gym Client, 3 mo in). Entry state: Both authenticated; same WebSocket Session.
  1. Priya drags the visual cable-pin to slab 8 (40 kg), reps target 12, RIR target 2. Set 1 row appears instantly on Aarav's app. She flips warm-up toggle on set 1.
  2. Aarav performs the set; either party can tap "Done" — last-write-wins. Auto-rest timer starts (isolation default 60 s); haptic at 10 s remaining.
  3. Sets 2-4: load bumps to slab 10 (50 kg). Aarav misses rep 9 → Priya flags rep 9 as spotter-assisted; rep 10 stays unrecorded. Set 3 prescribed 50/10 but actual 47.5/10 — both shown.
  4. Set 4 = failure set: Priya flips "to failure" → RIR target locks to 0. Aarav hits 8 reps actual, RIR derived = 0. Progression Index recomputes live.
  5. Priya tap-pairs the next exercise (face-pull) as a superset; tap-drops a band-only drop set after the failure set.

Climax: Set 4 → e1RM PR detection clears prior best by 1.2 kg. PR moment screen fires; both see it.

Resolution: Session ends; recovery chip updates (Back: red, 28h). Progression Index, e1RM graph, weekly volume all refresh.

Edge case: Network drop → offline banner, queued writes; reconnect reconciles last-write-wins. Disconnect rate > 5% trips SM-C2.

UJ-2. Rohit attempts a 200 kg squat PR, solo.

Persona: Rohit (Solo Client, no PT, no gym). Week 8 of curated 5×3 squat block.
  1. Warm-up sets 1-3 marked from set-row long-press menu (excluded from volume + Index).
  2. Working sets 1-4 hit 195/3 clean. Set 5 prescribed edited to 200 kg via barbell visualizer (snaps 25 + 25 + 20 + 10 per side; auto-sum 200).
  3. Set 5: rep 1 unassisted, rep 2 spotter-assisted (rep-quality bar after set). RIR actual = 0.
  4. App detects 1RM load PR AND e1RM PR.

Climax: PR composer fires. Cinematic amber. Three aspect ratios (square / 9:16 / 4:5). Rohit picks 9:16 → native share-sheet → Instagram Stories.

Resolution: Set saved with assistance metadata; card archived; Progression Index recomputes accounting for the spotter-assisted rep.

Edge case: PR dismissed without share → still archived; surfaced as a "you have an unshared PR" nudge once. SM-C10 watches.

UJ-3. Aarav signs up under Priya in his first seven days.

Persona: Aarav (Gym Client). Anita pre-imported his CSV row when he paid.
  1. QR scan → Google sign-in → roster match → ~10-field Onboarding Questionnaire (skippable advanced section).
  2. Trainer browse at his branch. Priya's card: certs verified, 4 yrs exp, hypertrophy + novice specialties, 4.8 rating, ~2h response, Hindi + English. Aarav picks her #1 + two fallbacks.
  3. Priya gets FCM push → reviews questionnaire → accepts. Aarav's home unlocks the trainer panel.
  4. Priya picks Vis "PPL Beginner 12-week" starter template → edits 3 swap-outs → assigns as a phased plan (phases 1/2/3).
  5. Aarav sees today's workout + 12-week grid + trainer card. First session tomorrow.

Climax: Day 7 — 3 sessions complete, adherence 100%, first PR detected.

Resolution: Steady state. Plan-block T-2 reminder scheduled for week 4 minus 2 days.

Edge case: #1 trainer doesn't respond within 24h → next-in-priority gets request. All three decline → marketplace browse path opens. Trainer can decline + transfer with client consent.

4. Features

Feature blocks A-K. FRs numbered globally (FR-1 through FR-43) so downstream artifacts reference stably. Numbering is NOT a build-order signal — FR-1 (Co-Edit) structurally depends on FR-3 (Set schema), FR-7 (Rest Timer), FR-8 (Equipment-Aware Logger), and FR-12 (AI Progression). Epic / sprint sequencing decisions belong to the architecture + sprint-planning phase. Inline UJ references mark which journey a capability realizes.

4.1 Block A — Trainer↔Client In-Person Sessions

Description: The signature surface. Trainer and client edit the same Session on two devices simultaneously during the workout. All set rows accept prescribed AND actual values, warm-up flag, failure intent, RIR target, per-rep assistance tags. Progression Index updates after every working Set. UJ-1, UJ-2

FR-1 Co-edited Session

Trainer and Client can edit the same Session on two devices via WebSocket. Last-write-wins per Set row.

Consequences (testable):
  • Trainer edits Set 1 reps from 10 → 12; within ≤ 500 ms Client's UI reflects 12.
  • Both devices write to the same Set within 50 ms of each other → final value matches the later server-received write; conflict logged.
  • WebSocket disconnect → offline banner; writes queue; reconnect sync within 5 s.

FR-2 Warm-up vs Working Set distinction

Either party can flag any Set row as warm-up. Warm-up Sets excluded from Progression Index, total-volume PR detection, weekly volume metrics. UJ-1

FR-3 Prescribed vs Actual fields per Set

Every Set stores prescribed_load, prescribed_reps, actual_load, actual_reps, rpe_target, rpe_actual (1.0–10.0 in 0.5 steps), source ∈ {TRAINER, AI, AI_BOOTSTRAP}, ai_locked boolean. Progression Index reads actual. UI shows prescribed + actual when divergent; RIR (10 − RPE) toggleable per user. UJ-1, UJ-3

FR-4 Failure-intent flag + derived RPE

Trainer can flag a Set as "to failure". rpe_target locks to 10.0 (RIR = 0); rpe_actual measured from rep velocity or trainer/user input. UJ-1, UJ-2

FR-5 Per-rep Assistance tagging

User labels each rep within a Set as unassisted | spotter_assisted | forced. UI is a rep-quality bar after the Set. Affects PR detection (forced reps disqualify load-PR; spotter-assisted halves Progression Index credit [ASSUMPTION]). UJ-2

FR-6 Superset + Drop-Set composition by gesture

Tap-to-pair adjacent exercises composes a Superset. Tap-to-drop on a Set then engaging the Equipment-Aware Logger picks the drop weight. No typing. UJ-1

FR-7 Rest Timer

Auto-starts on Set save. Defaults: compound 2-3 min, isolation 60-90 s. Trainer override per (client × exercise). Haptic cue at 10 s remaining.

Consequences:
  • Saving a compound lift Set starts a 150 s timer (default).
  • Trainer override "120 s" persists across Sessions for that (client × exercise).

FR-8 Equipment-Aware Logger (six equipment types)

User logs Set load via the visualizer that matches the equipment.

EquipmentLogger pattern
Cable pin-stackDrag visual pin to slab position
BarbellTap plates onto each side; auto-sum to total
DumbbellNumber-line slider; kg/lb toggle; rack increments snap
Machine pin-stackSame pattern as cable
BodyweightBody silhouette + optional weight-vest field
KettlebellDiscrete-step picker matching standard kettlebell weights
BandsColor-coded resistance-tier picker

Numeric-keypad fallback always available. Defaults to last-used load for (user × exercise). One-tap "same as last set" / "same as last session". UJ-1, UJ-2, UJ-3

Consequences:
  • Opening cable exercise pre-loads the last slab position used.
  • Picking 25 + 20 + 10 kg per side renders barbell visualizer totaling 130 kg (60 plates + 20 bar).
  • Voice fallback parses "fifty for ten" → 50 / 10 [ASSUMPTION: voice fallback v1 scope].
Feature-specific NFRs NFR:
  • Set save → server commit ≤ 250 ms p95.
  • Visualizer first-contentful render ≤ 200 ms after exercise tap.
[NOTE FOR PM] Equipment-aware loggers are the single biggest UX investment in v1. Cutting any one (e.g. bands) reduces the differentiator. Revisit at Finalize only if scope-pressure escalates.

4.2 Block B — Solo Program Builder + PR Cards

Description: Self-directed clients with no PT get a curated template marketplace, Equipment-Aware Logger, Progression Index, e1RM graph, PR detection, PR Card composer. No AI programming (cost containment; v2). UJ-2

FR-9 Template Marketplace for Solo Clients

Vis ships ~15 curated public Plan Templates v1 (5×5, nSuns, PPL, RP-style hypertrophy + Vis starters). User picks → edits → assigns to weekly grid. Blank-slate builder is v2.

FR-10 PR Detection (four dimensions)

System detects PRs across: 1RM load, e1RM, total-volume per Session, rep-count-at-given-load. Detection runs immediately after each Set save. UJ-2

Consequences:
  • Set actual_load > prior max → 1RM PR fires.
  • e1RM via actual_load × (1 + actual_reps/30) > prior max → e1RM PR fires [ASSUMPTION: Epley].

FR-11 PR Moment Screen + Card Composer

On PR detection, cinematic moment screen (amber animation). One Vis template, three aspect ratios (square / 9:16 / 4:5). Native share-sheet to Instagram, Stories, WhatsApp Status, X, camera roll. Vis watermark default ON, user-togglable OFF per share; toggle state persists across future shares. Locked at Finalize 2026-05-22. UJ-2

4.3 Block C — Progression Engine

Description: The brain. AI-suggested progression v1 — Claude proxy with prompt caching writes next prescribed Set per (trainer × client × exercise). Trainer reviews + accepts or overrides via ghost overlay. AI is trainer-only v1 (cost containment); solo clients see AI-bootstrap defaults at first assignment then self-direct. Four additional rule types (double-progression, linear, RPE-based, DUP) deferred to v1.5. UJ-1, UJ-2, UJ-3

FR-12 AI Progression Rule per (trainer × client × exercise)

System computes next-Set targets via Claude proxy with prompt caching. Inputs: last N=12 Sets' (load, reps, rpe_actual), client goal, exercise class, days-since-last-session. Output: {prescribed_load, prescribed_reps, rpe_target, decision ∈ {MAINTAIN, BUMP_REPS, BUMP_WEIGHT, DEMOTE}}. Persisted per (trainer × client × exercise). On client switching trainer, AI history persists; new trainer adopts or resets. UJ-1

Consequences:
  • Toggling AI on for (Priya, Aarav, squat) → ghost suggestion on next session's squat exercise.
  • Prompt cache hit-rate ≥ 80% on repeat suggestions for same (client × exercise) within 7 days.
  • AI cost / WAU > $0.40 / mo trips SM-C1.

FR-13 AI Bootstrap (first-assignment cold start)

On first exercise assignment with no prior Set history, system computes bootstrap prescription from: client questionnaire (experience, goal, sex, age), exercise compound/isolation class, conservative starting-load heuristic (≈ 50% bodyweight × experience-factor for compounds; isolation defaults). source = AI_BOOTSTRAP. UJ-3

Consequences:
  • Aarav (novice, 78 kg) starts squat → bootstrap prescribed 40 kg × 8 @ RPE 7.
  • First completed Set transitions source from AI_BOOTSTRAP to AI for subsequent suggestions.

FR-14 Next-Suggested ghost overlay + ai_locked toggle

Next prescribed value rendered as ghost overlay on Equipment-Aware Logger. One-tap "use suggestion" or trainer override. Per-(trainer × client × exercise) ai_locked toggle removes the override surface (autopilot mode). UJ-1, UJ-2

Consequences:
  • Ghost overlay in --vis-amber-highlight; tap = accept; long-press = override.
  • ai_locked = true hides override controls; trainer can still unlock per (client × exercise).
  • Trainer-override rate > 70% trips SM-C5 (AI failing).

4.4 Block D — Gym Staff / Branch Manager Operations

Description: Anita's surface. Member lifecycle, payment logging, PT activation, reminders. Branch-scoped. UJ-3

FR-15 Member CSV / Excel Import

Staff uploads CSV mapping: name, phone, email, membership_type, membership_start/end, pt_start/end, trainer_assigned. Duplicate detection by phone number. UJ-3

FR-16 PT Activation

Staff activates, suspends, expires a member's PT. State drives Client App access gate (FR-43).

FR-17 In-person Payment Logging

Staff records cash / UPI / card payment amount, date, member, PT block extension. Generates audit-log entry (FR-26).

FR-18 Reminder Cadence

Staff triggers WhatsApp / FCM reminder templates: PT expiry, missed sessions, payment overdue. v1 = generate-and-copy templates (P0); WhatsApp Business API direct send is P1.

FR-19 Trainer Cert Verification (admin gate)

Trainer uploads cert; gym admin (Staff or Owner) reviews + approves → badge appears on trainer's public profile. P0.

4.5 Block E — Gym Owner Cross-Branch Operations

Description: Vikram's surface. All branches, trainers, revenue. Brand-scoped (no cross-brand visibility).

FR-20 Cross-Branch Revenue Dashboard

Per-branch + brand-aggregate revenue, PT activation count, churn, trainer utilisation. Configurable date range.

FR-21 Trainer Leaderboard

Per-branch + brand-wide rankings on three independent dimensions:

  • Experience — years active as Trainer in Vis-recognized practice (self-attested + cert-verified per FR-19).
  • Client Feedback — mean of post-PT-block 5-star ratings; minimum n=3 ratings to qualify.
  • Client Progress — median Progression Index Δ across the trainer's active clients over a rolling 90-day window. Δ per (client × exercise) = (current Index − Index 90d ago) / Index 90d ago × 100. Aggregated as median across active client pool.

Feeds Client onboarding-browse surface.

FR-22 Branch Health Snapshot

Per-branch KPIs: active members, active PT, WALS, adherence avg, trainer-cert-pending count.

FR-23 Brand-Wide Audit Log Read

Owner reads brand-wide audit log (FR-26). Cannot edit history.

4.6 Block F — Cross-Role Gym Surfaces

FR-24 Trainer Public Profile Card

Fields: name, photo, certifications + verified badge, years experience, specialty tags, client rating, response-time stat, languages. Visible in client browse + on assigned client's home. UJ-3

FR-25 Client-Chosen Trainer Assignment (gym path)

Client picks top 1-3 trainers in priority order; first-come-first-serve accept. Trainer can decline + transfer with client consent, carrying Questionnaire + Plan. UJ-3

Consequences:
  • Server enforces single-active-state invariant on (client_id, trainer_id, request_status=PENDING): simultaneous trainer-decline + client-cancel-and-reissue collapses to one winning write by server-stamped monotonic order; loser receives no-op + UI banner.
  • Trainer accept while client already cancelled → trainer sees "client withdrew" toast; no PtActive created.
  • Two trainers accept at same instant → first server-stamped accept wins; second receives "already assigned".

FR-26 Audit Log (P0)

Append-only log of: member edits, payment edits, role changes, plan-template publishes. Branch-scoped reads (Staff); brand-wide reads (Owner). Compliance + integrity.

4.7 Block G — Onboarding & Plan Lifecycle

Description: Two onboarding paths sharing one Questionnaire; one Plan model serving both flat and phased with expiry-aware reminders. UJ-3

FR-27 Onboarding Questionnaire (~10 fields)

Fields: age, sex, height (cm/in), weight (kg/lb), experience, gap (months sedentary), body-type, primary goal, injuries (free-text), days/week, equipment, wearable opt-in. Optional advanced: sleep avg, calorie estimate. Drives trainer-browse defaults + plan-template suggestions. UJ-3

FR-28 PT Relationship State Machine

NoPt ──── invite + accept ────► PtActive
PtActive ──── either-party end ────► PtEnded
PtEnded ──── new invite + accept ────► PtActive
PtEnded ──── (inactive threshold) ────► NoPt  [ASSUMPTION]

On PtEnded, the prior Trainer retains read-only access to past Plans they authored + alumni list. No re-engagement messaging v1.

Mid-Session PT-end rule: if either party terminates PT while a Co-Edit Session is in flight, server freezes new writes, flushes WebSocket queue (acked writes ack; pending return 409 conflict), and marks Session terminated_during=true. Session readable to both parties (and prior trainer, read-only).

FR-29 Plan Builder — Flat or Phased

Trainer authors a flat Plan OR a phased Plan (named blocks with start + end dates). Phase transitions explicit + client-visible. Plan validity window with expiry reminders via FCM.

FR-30 Plan-Block Expiry Reminders

Trainer receives FCM push at T-2 days before Plan or Phase expiry, and at expiry, until acknowledged or new Plan/Phase assigned. UJ-3

FR-31 Plan Templates (three sources)

Trainer sees: (1) Vis starter library (~15 templates v1), (2) per-trainer private, (3) brand-shared. RBAC determines edit / publish rights. UJ-3

FR-32 Cardio Logging

v1 covers treadmill, elliptical, bike, rowing, free-form. Fields: mode + duration + avg HR + perceived effort. Equipment-Aware Logger doesn't cover these; minimal numeric + dropdown UI.

4.8 Block H — Solo Trainer Discovery & Marketplace

FR-33 Solo-Trainer Invite Link

Solo Trainer has a personal share link (default). Sharing routes a new client into the trainer's direct request inbox.

FR-34 Trainer Marketplace (opt-in)

Solo Trainer can opt in to the Vis-wide marketplace. Filters: specialty, certification, language, rating, response time. Trainer-side moderation queue flags abuse / fake profiles. Marketplace abuse > 1% trips SM-C7.

[NOTE FOR PM] Marketplace defer-to-v1.5 is a Finalize scope-pressure option (decision-log scope-risk flag).

4.9 Block I — Recovery, Volume, Load Monitoring (shared client tabs)

FR-35 Muscle Recovery Status

Color-coded chips per muscle group (Chest, Upper Back, Lower Back, Shoulders, Biceps, Triceps, Forearms, Quads, Hamstrings, Glutes, Calves, Core). Computed from last Session training that group. Green = recovered; red = hours remaining.

FR-36 Per-Muscle Weekly Set Count

System tracks working Sets per muscle group per week (rolling 7-day window). Chip per muscle group on Progress Tab: current vs Schoenfeld-derived ceiling (≈ 20 sets / muscle / week for hypertrophy). Amber 16–20; red > 20. Source: domain research §training-science.

Consequences:
  • Aarav has logged 14 chest Sets this week → chest chip displays "14 / 20"; green state.
  • Logging Set 21 → chest chip flips red + Trainer App notification (if PT-attached).

FR-37 ACWR Trainer Alert

System computes Acute:Chronic Workload Ratio per client per week (acute = last 7d volume; chronic = trailing 28d rolling avg). When ACWR > 1.5, Trainer App fires amber alert on client profile card. ACWR > 2.0 → red + auto-deload via FR-12 ghost overlay (next Session: 70% prescribed loads). Source: IOC-grounded.

Cold-start suppression: first 14 calendar days of any client's logging history, ACWR alerts suppressed (chronic baseline not yet representative). Trainer App shows "baseline-building (day X / 14)" chip instead. After day 14, chronic computed from available window even if < 28 days, with "preliminary" qualifier until day 28.

FR-38 Progress Tab

Body Measurements over time (weight, body fat %, chest/waist/hip/arm/thigh — line charts). Strength Progress (e1RM per exercise over time). Attendance Calendar heatmap. Per-muscle weekly set-count strip (FR-36). ACWR sparkline (FR-37) visible to client + trainer.

FR-39 Profile Tab

Name, photo, branch (if gym), membership + PT expiry, default daily visit time + per-day overrides + rest days, fitness goals, current body stats summary, assigned trainer card.

4.10 Block J — Nutrition (Trainer-Authored)

Description: Trainer authors per-client daily macro target + meals breakdown. Client reads only. No AI macro generation v1 (v2 candidate). Restored from original spec §7.6.

FR-40 Trainer Macro Plan Authoring

Trainer App provides per-client daily macro editor: total calories, protein (g), carbs (g), fat (g), water (L). Optional weekly variants (higher-carb on training days). Free-text guidance field (200 char).

Consequences:
  • Trainer saves Aarav's macros: 2600 kcal / 180P / 280C / 80F → reflected on Aarav's Nutrition tab within next app open.
  • Weekly variant "training-day" overrides default on assigned workout days only.

FR-41 Client Nutrition Tab (read-only)

Client App Nutrition tab displays: today's macro targets, meals breakdown (Breakfast, Pre-workout, Lunch, Post-workout, Dinner), per-meal food items + quantities + macros, water intake target. Read-only. No client edits v1.

4.11 Block K — Authentication & Access Gate

FR-42 Authentication

Google Sign-In, Apple Sign-In (iOS required), Phone OTP via Firebase Auth. Backend (Spring Boot) validates Firebase JWT on every request.

FR-43 Access Gate by Role

Solo path: any authenticated user lands on solo onboarding. Gym path: user record matched on phone / email against brand's roster; if no match → "pending activation" screen until Staff activates. PT lapse → "PT membership expired" screen (data retained).

5. Non-Goals (Explicit)

  • Not a group-fitness app. Class booking + class attendance out (v2 candidate).
  • Not a payment gateway. Vis logs in-person payments staff make; Vis does not process them.
  • Not a wearable / Apple Watch app v1 (addendum §5).
  • Not a messaging platform. Trainer↔client communication outside Sessions on WhatsApp; Vis ships template generation + send-link only.
  • Not a video content platform. Exercise demos = static images / links v1; trainer-uploaded videos = v2.
  • Not a member-facing web portal. Clients are mobile-only.
  • Not writing to Apple Health / Google Fit. Read-only on device; not stored backend-side.
  • Not an AI coach for solo users v1. AI = Trainer-only.
  • Not multi-region v1. Cloud Run asia-south1 only.
  • Not offering SMS v1. v1 = FCM push + email transactional.

7.2 Real-Time Sync

  • WebSocket transport for Co-Edit sessions. Reconciliation: last-write-wins per Set row.
  • WebSocket disconnect rate > 5% trips SM-C2.
  • Offline queue persists pending writes; reconnect drains within 5 s.

7.3 AI

  • Trainer-only feature v1. Solo users do not see AI surfaces.
  • Claude proxy with prompt caching; cache target ≥ 80% hit rate on (trainer × client × exercise) repeats.
  • Cost ceiling: $0.40 / WAU / month (SM-C1). Runtime circuit-breaker: at $0.80 / WAU rolling-7-day average, system auto-throttles (cap one suggestion per (client × exercise) per 24 h; otherwise served from cache). $1 / WAU triggers pivot.
  • API failure fallback: on Claude error (empty / null / HTTP 5xx), ghost overlay falls back to last-prescribed value with stale-ai indicator. Trainer can manually override.

7.4 Compliance + Privacy

  • DPDPA (India): consent capture at onboarding; right-to-erasure flow in Profile → Account → Delete.
  • GDPR readiness: same erasure + portability surfaces enabled globally.
  • DPDPA support tickets > 0.5% WAU / wk trips SM-C4.
  • Body measurement + health-derived data classified Sensitive; encrypted at rest; never logged in plaintext.

7.5 Performance

  • Set save → server commit p95 ≤ 250 ms (SM-C6).
  • Equipment-Aware Logger first-contentful render ≤ 200 ms.
  • App cold start ≤ 2.0 s on mid-tier Android (Pixel 6a / Galaxy A54 target).
  • Admin Web FCP ≤ 1.5 s broadband; LCP ≤ 2.5 s.
  • Idempotency: every Set write carries client-generated UUID; server dedupes by UUID; on logger crash + retry same UUID returns prior commit (no double-writes, no silent loss).

7.6 Notifications

  • v1: FCM push + email transactional.
  • Reminder events: PT expiry, plan-block expiry T-2 / T-0, missed session, trainer client-request, PR shareable.
