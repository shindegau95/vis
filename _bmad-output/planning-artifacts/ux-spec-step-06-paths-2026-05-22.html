UX Spec · Step 06 · Design System Choice

Pick a foundation for Vis's three apps

2026-05-22 · Author: Gauravprakashshinde · Three paths, one decision
Vis ships brand-distinct UI across React Native (Client + Trainer) and Angular (Admin Web). The question is what sits under the brand layer — pure custom, themeable foundation, or off-the-shelf component lib. The brand layer is custom either way; this choice decides the primitives layer.

What's already locked (regardless of path)

Vis-original · non-negotiable

Brand layer — custom, no library

  • Tokens: two-layer system from step-05 (Layer A raw amber + brand-locked + future presets; Layer B semantic --accent / --brand-locked-*).
  • Visual: orb-as-organism with 5 tension states; Vis wordmark; cinematic amber palette; Geist + Geist Mono; warm ivory bg; peach shadows; Liquid Glass on nav + hero only.
  • Signature components (custom-built, no lib): Equipment-Aware Logger (6 variants), Connection Orb, Recovery Orb, PR Moment composer, Branch-Scope Chip, Active Session Set row.
  • 21st-dev/magic MCP used for component scaffolding (per CLAUDE.md), then adapted to Vis tokens regardless of path chosen.

The three paths

Each path describes the layer under the brand layer — the primitives that handle a11y, focus, overlays, gestures, theming.

Path A · Pure custom

No UI library underneath

Build every primitive from React Native StyleSheet + Angular components from scratch. Maximum control, maximum build cost.
Stack
  • RN: bare StyleSheet + custom ThemeProvider
  • RN: Reanimated 3 + Gesture Handler (animation + gesture)
  • Angular: pure Angular + custom CSS (no Material, no PrimeNG)
  • A11y: hand-roll focus traps, ARIA, screen-reader labels
Pros
  • Zero brand dilution
  • No vendor lock
  • Smallest bundle
  • Exact behaviour control
Cons
  • A11y primitives = months of hand work
  • Focus / portals / dialogs / modals all re-derived
  • Slow to v1
  • Quality bar risk on WCAG AA
★ Recommended Path B · Themeable foundation

Tamagui (RN) + Tailwind + Angular CDK (web)

Themeable primitives that respect Vis tokens; brand layer stays custom; a11y comes for free from CDK + Tamagui ARIA.
Stack
  • RN: Tamagui — token-driven (matches Layer A/B), cross-RN/web, animation built-in
  • RN: Reanimated 3 + Gesture Handler for Equipment-Aware Logger gestures
  • Web: Tailwind CSS utility classes + custom Angular components
  • Web: Angular CDK (a11y, overlays, drag-drop, portal, focus trap) — headless, no Material visual on top
  • Icons: Lucide (RN + Angular ports) — restrained line icons
  • Fonts: @fontsource/geist + Geist Mono, self-hosted
  • Charts: Victory Native (RN) + Apache ECharts (Angular) — both themable
Pros
  • Token system fits Tamagui's createTheme natively
  • A11y primitives from Angular CDK + Tamagui
  • Animation perf built-in (Reanimated worklets)
  • Time-to-v1 ~30% faster than Path A
  • WCAG AA comes mostly free
Cons
  • Tamagui learning curve
  • Tailwind ≠ token-source (need bridge layer)
  • Two icon-lib ports to keep in sync
Path C · Off-the-shelf libs

React Native Paper (RN) + Angular Material (web)

Fastest-to-v1. Costs visual differentiation. Material aesthetic fights cinematic restraint.
Stack
  • RN: React Native Paper (Material) OR NativeWind
  • Web: Angular Material (Material visual)
  • Override theme tokens; restyle every component
Pros
  • Fastest scaffold
  • Mature a11y
  • Largest component coverage
Cons
  • Material aesthetic ≠ cinematic amber
  • Override cost erases speed gain
  • Brand dilution risk — "looks like every other app"
  • Restyling Material is harder than building custom on Path B foundation

Why Path B

  • Vis's two-layer token architecture (locked in step-05) maps directly to Tamagui's theme system — Layer A raw tokens become Tamagui's createTokens input, Layer B semantic tokens become Tamagui's createTheme output.
  • The brand layer (orb, wordmark, Equipment-Aware Logger, Connection Orb, PR Moment) is custom-built in all three paths — Path B just removes the "rebuild a Dialog primitive" tax.
  • Angular CDK gives WCAG-AA primitives for free (focus trap, live region, overlay positioning) — saves weeks vs Path A.
  • Light + dark theme parity v1 is one config file in Tamagui — Path A means writing parity by hand for every component.
  • The accent-presets architecture (deferred to v1.1) is a one-line theme switch in Tamagui; Path C means re-overriding the entire Material palette per preset.
  • 21st-dev/magic MCP scaffolding (mandated by CLAUDE.md) adapts cleanly to any path — but Path B's themable primitives accept generated components with minimal rewiring.
